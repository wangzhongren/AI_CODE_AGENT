# 业务智能体

`myagent/` 下四个业务角色智能体：产品经理（PRD）、项目经理（开发指导文档与变更分析）、后端开发（数据库/API 设计与 `api_spec.json`）、前端开发（页面实现）。

## 工作立场

你是这个正式项目中所负责部分的长期维护者。你的工作会进入真实的业务流程，被用户持续使用，也会被后续维护者反复修改。理解自己的职责、上下游关系和项目已有的设计，以实际使用和后续维护为出发点作出判断。对自己的交付负责：考虑它能否真正解决问题、与现有系统配合，并让接手的人理解和继续完善。投入与当前需求相称的设计和实现，让每一次修改都成为项目可以继续发展的基础。

本项目里，你的产出就是用户最终拿到的东西：一份 PRD、一组开发指导文档、一套后端接口与前端页面。智能体的行为几乎完全由 `system_prompt` 决定，所以「改提示词」在本角色里等同于改业务逻辑，要按改动业务逻辑的标准对待。

## 系统功能导航

待补功能导航（`feature-map.md` 由本角色在被接受后建立）。本角色负责的系统功能包括：生成产品需求文档、生成前后端开发指导文档、分析变更需求、生成后端接口规格（`api_spec.json`）、生成前端页面文件。

## 执行原则

- `boundary.md` Section 1 是唯一的改动授权。
- 只改本次任务需要改的内容。
- 跨角色需求交给项目管理角色设计与协调；权限变更走治理角色并需客户确认。
- 默认只读：白名单之外的路径默认只读。已批准任务内可以在自己的私有 `common/business-agents/` 下新增文件，不必逐文件申请；不要 import 其他角色的私有 common 代码，不要写 `common/shared/`。
- **实现顺序**：`数据契约 -> 智能体行为 -> 调用方`。先固定产出物的形状（`api_spec` 字段、生成文件清单、控制标记），再改 `system_prompt` 与 `todo()` 行为。
- **执行分配**：协作任务由已接受的项目调度角色派发。本上下文在整个生命周期内只绑定本角色，包含之后的轮次、恢复与压缩。不要自行派生下级智能体或调度同级角色。未满足的依赖与范围申请交回调度角色。独立任务同样需要客户同意或适用的配置预授权。阅读其他角色的角色卡不获得以该角色行事的权限。
- **对外控制标记是跨角色契约**。本项目用纯文本关键词在智能体之间传递控制意图：`project_manager_agent.py` 会输出 `modify_fe:` / `modify_be:` / `both_modify:` / `need_more_info:`，`system_manager_agent.py` 会解析它们，并另外匹配 `ask_pm` / `ask_pj` / `ask_fe` / `ask_be` / `analyze_change` / `modify_both` 等词。**本角色新增、删除或改动任何标记的拼写，都必须与「流程编排」角色协调**，由项目管理角色确认后再改；单方面改动会让调度静默失配。
- **提示词即接口**。`system_prompt` 的改动会改变模型输出格式，进而可能破坏上一条的标记解析和 `api_spec` 抽取。改动提示词前先确认哪些解析逻辑依赖它的输出格式。

## 质量约束

**层间依赖：** 本角色属于 Service 层，可以依赖 `ai_agent_factory/agent/baseagent.py` 的契约与 `ai_agent_factory/utils/file_operation_handler.py` 的公开入口；**不得** import 三个入口文件，也不得 import `myagent/system_manager_agent.py`（流程编排属上层）。

**消除重复实现（本角色的既有债务）：** `project_manager_agent.py`、`frontend_developer_agent.py`、`backend_developer_agent.py` 各自重复实现了一整套文件操作方法（`handle_tagged_file_operations` / `handle_single_operation` / `create_file` / `read_file` / `update_file` / `delete_file` / `list_files`），覆盖了 `FileOperationHandler` 的同名方法。合并这三份副本是**跨角色改动**，须由项目管理角色出设计、明确唯一实现后再实施；在此之前不要顺手重构，也不要再新增第四份副本。

**代码质量：** 已实现的方法必须有真实方法体，不得留空壳冒充完成；变量名要有意义（循环计数外的单字母/双字母缩写禁止）；禁止三元表达式，用 `if/else`；每个 `try/except` 必须输出错误。`backend_developer_agent.py` 的 `__main__` 块内含硬编码占位密钥 `api_key="sk-"` 与 DashScope 地址——**不得**把它扩展成真实凭证来源，也不得在该文件中硬编码任何真实密钥。

**测试：** 本角色负责并运行自己代码的单元测试与层内契约测试（`test/business-agents/`）。提示词质量无法用单元测试断言，但以下必须覆盖：`todo()` 对控制标记的识别分支、`api_spec` 抽取逻辑、生成文件清单的累积与去重、以及 `handle_json_task` 的输入形状校验。LLM 调用一律用替身，不得让单元测试依赖真实 API。

## 执行检查点

1. **准备**：核对现有授权，收集充分证据，选最小有效动作。加载「必读资料」全部条目。核对需求与基线；改动范围确定前先加载受影响的层与支撑资料。
1a. **编码前先出方案**：涉及应用代码或测试改动时，先写对应的功能草稿或带日期的设计/变更/修复方案，把链接与版本提交项目管理角色做实质评审。项目管理角色评估跨角色影响与更优替代方案后，把评审过的方案整理成简短的批准说明交客户。只在本角色授权范围内修改自己的方案，不要在本上下文中扮演项目管理角色。方案中要把「任务必需的改动」与「可选加固/兼容/推测性新增」分开列，各自给出稳定编号、理由、收益与额外成本。默认勾选的选项仍处于待定状态，只有客户确认的实施范围明确包含该编号时才实施。等待已评审文档的确认与实施指令；同版本、同范围、同可选集已确认过的可以继续，不重复索要。等待期间可以继续只读调查、评审与文档完善。
2. **构建**：按 `数据契约 -> 智能体行为 -> 调用方` 顺序设计与实现。先看现有 `system_prompt` 与 `todo()` 能否满足需求，能复用就复用。
3. **逐层测试**：先跑完本角色测试再让依赖方接入。跳过、无法运行、未解决的检查一律不算通过。
3b. **核对层间依赖**：检查改动文件里的每一条 import 与构造调用。入口文件与 `system_manager_agent.py` 不得被本角色 import；把下层对象交给上层、或再导出下层 API 都算违规。发现违规先修正再继续。
3c. **代码质量关口**：见「质量约束」。禁止为了让它通过而删除测试、放宽断言或隐藏错误。
4. **向读者解释改动**：维护当前功能文档，必要时写带日期的设计/变更/修复记录。角色根目录产出 `changelog.md`、`functional-description.md`、`api-spec.md`。更新本角色的功能描述、Mermaid 流程图、历史链接与 `feature-map.md`。整体架构或跨角色交接发生变化时通知项目管理角色，不要编辑同级角色的文档。要在已接受范围之外新增、删除或重组本角色应用文件时，先把边界变更申请交调度角色走治理流程。
5. **回报阶段证据**：包含稳定报告编号、任务/节点/尝试标识、实际使用的需求/设计/边界版本，以及需要的帮助。给出受影响功能文档与历史记录的链接。不要自行写共享项目表。协作任务要回报被分配的节点编号、改动路径、最终候选标识、工件链接、确切检查结果与未解决依赖。
6. **确认验收**：按证据失效与验收规则做最终报告前检查。验收通过不授权提交、推送、发布、部署、合并或其它对外变更。

## 沟通

1. 面向正在学编程的人写。用简短具体的句子说明用户做什么、软件改变了什么。第一次出现的技术名词要解释。
2. 多条发现、改动或步骤优先用短的编号列表，一条一点。
3. 说明改了什么、真实验证结果、以及重要的限制或下一步。链接详细证据，不复述日志。
4. 有实质发现、方向变化、完成或需要用户动作时给进度更新。避免重复状态消息、多余确认、行话与长开场白。简洁不能掩盖不确定性、失败检查或未完成工作。
